# eRynok — Online Marketplace API

**eRynok** — навчальний проєкт REST API для онлайн-маркетплейсу, який дозволяє продавцям розміщувати товари, покупцям додавати товари до кошика та створювати замовлення, а адміністраторам керувати системою.

## 1. Опис системи

Система призначена для організації взаємодії між продавцями та покупцями в межах онлайн-маркетплейсу.

API надає можливості для управління користувачами, товарами, категоріями та замовленнями. Для автентифікації та авторизації використовується **ASP.NET Core Identity** та **JWT (JSON Web Token)**.

Для зберігання даних використовується **Microsoft SQL Server**, а взаємодія з базою даних реалізована за допомогою **Entity Framework Core**.

Проєкт побудований на основі розділення відповідальності між контролерами, сервісами, репозиторіями, моделями та DTO.

## 2. Предметна область

У системі передбачено три ролі користувачів:

- **Seller (Продавець)** — може створювати товари та керувати власними товарами, переглядати замовлення на свої товари й змінювати їхні статуси.
- **Buyer (Покупець)** — може переглядати товари, додавати їх до кошика, змінювати кількість товарів, видаляти власні замовлення та переглядати історію замовлень.
- **Admin (Адміністратор)** — має розширені права для управління користувачами, товарами, категоріями та замовленнями.

Основні об'єкти предметної області:

- **Користувач** — обліковий запис учасника маркетплейсу.
- **Профіль продавця** — додаткова інформація про продавця.
- **Профіль покупця** — додаткова інформація про покупця.
- **Категорія** — група, до якої належать товари.
- **Товар** — позиція, яку продавець розміщує на маркетплейсі.
- **Замовлення** — запис про замовлення певного товару покупцем із зазначенням кількості, ціни та статусу.
- **Група замовлень (OrderGroup)** — об'єднує замовлення одного покупця та використовується для реалізації його кошика.

Одне замовлення містить один товар. Під час створення замовлення система фіксує поточну ціну товару, тому подальша зміна ціни в каталозі не впливає на вже створене замовлення.

Кожен покупець може мати лише одну групу замовлень, яка використовується як його кошик. Додавання товарів до кошика створює нові записи замовлень або доповнює наявну групу.

## 4. Основні можливості

### Автентифікація та авторизація

- Реєстрація покупців і продавців.
- Вхід у систему за електронною поштою та паролем.
- Генерація JWT-токена після успішної автентифікації.
- Отримання інформації про поточного авторизованого користувача.
- Розмежування доступу до API відповідно до ролей.
- Захист маршрутів за допомогою `[Authorize]`.

Публічна реєстрація доступна для ролей Buyer та Seller. Створення адміністратора виконується окремо під час початкового налаштування системи.

### Управління товарами

- Створення товарів продавцями.
- Перегляд доступних товарів.
- Пошук товарів за назвою та описом.
- Фільтрація за категорією, продавцем і ціною.
- Редагування та видалення товарів.
- Адміністратор може створювати й редагувати товари, зокрема призначати їм продавця.

### Управління категоріями

- Перегляд списку категорій.
- Пошук категорій.
- Створення, редагування та видалення категорій адміністратором.

### Управління кошиком і замовленнями

- Додавання товарів до кошика.
- Збільшення кількості товару, якщо він уже є в кошику.
- Зміна кількості товарів у кошику.
- Видалення власних замовлень зі статусом Pending.
- Перегляд власних замовлень покупцем.
- Перегляд замовлень продавцем.
- Фільтрація замовлень за покупцем, продавцем і статусом.
- Зміна статусу замовлення продавцем або адміністратором.

Кошик реалізований на основі `OrderGroup`. Додавання товару до кошика одразу створює замовлення зі статусом `Pending`. Окремого етапу підтвердження кошика в поточній реалізації немає.

## 6. Реалізовані endpoints

### Auth

| HTTP-метод | Endpoint | Опис | Доступ |
|---|---|---|---|
| POST | `/api/Auth/register` | Реєстрація користувача | Публічний |
| POST | `/api/Auth/login` | Автентифікація користувача | Публічний |
| GET | `/api/Auth/me` | Отримання інформації про поточного користувача | Авторизований користувач |

Після успішного входу сервер повертає JWT-токен, який використовується для доступу до захищених маршрутів.

### Products

| HTTP-метод | Endpoint | Опис |
|---|---|---|
| GET | `/api/Products` | Отримання списку товарів |
| GET | `/api/Products/{id}` | Отримання товару за ID |
| POST | `/api/Products` | Створення товару |
| PUT | `/api/Products/{id}` | Оновлення товару |
| DELETE | `/api/Products/{id}` | Видалення товару |

Підтримувані параметри фільтрації: `search`, `categoryId`, `userId`, `minPrice`, `maxPrice`.

Перегляд товарів доступний без авторизації. Операції створення, редагування та видалення доступні відповідно до ролей і прав користувача.

### Categories

| HTTP-метод | Endpoint | Опис |
|---|---|---|
| GET | `/api/Categories` | Отримання списку категорій |
| GET | `/api/Categories/{id}` | Отримання категорії за ID |
| POST | `/api/Categories` | Створення категорії |
| PUT | `/api/Categories/{id}` | Оновлення категорії |
| DELETE | `/api/Categories/{id}` | Видалення категорії |

Підтримуваний параметр пошуку: `search`.

Перегляд категорій доступний без авторизації. Керування категоріями доступне адміністратору.

### Users

| HTTP-метод | Endpoint | Опис |
|---|---|---|
| GET | `/api/Users` | Отримання списку користувачів |
| GET | `/api/Users/{id}` | Отримання користувача за ID |
| POST | `/api/Users` | Створення користувача |
| PUT | `/api/Users/{id}` | Оновлення користувача |
| DELETE | `/api/Users/{id}` | Видалення користувача |

Підтримувані параметри фільтрації: `search`, `role`.

### Orders

| HTTP-метод | Endpoint | Опис |
|---|---|---|
| GET | `/api/Orders` | Отримання списку замовлень |
| GET | `/api/Orders/{id}` | Отримання замовлення за ID |
| GET | `/api/Orders/cart` | Отримання кошика поточного покупця |
| POST | `/api/Orders` | Додавання товарів до кошика |
| PATCH | `/api/Orders/{id}/status` | Зміна кількості або статусу замовлення |
| DELETE | `/api/Orders/{id}` | Видалення замовлення |

Підтримувані параметри фільтрації: `buyerId`, `sellerId`, `status`.

Для створення замовлення використовується тіло запиту:

```json
{
  "items": [
    {
      "productId": 1,
      "quantity": 2
    }
  ]
}
```

Для зміни кількості товару покупець надсилає:

```json
{
  "quantity": 3
}
```

Для зміни статусу замовлення продавець або адміністратор надсилає:

```json
{
  "status": 1
}
```

Зміна кількості доступна покупцю лише для його власних замовлень зі статусом Pending. Продавець може змінювати статус замовлень лише на власні товари.

### Статуси замовлень

| Значення | Назва | Опис |
|---|---|---|
| 0 | Pending | Очікує обробки |
| 1 | Confirmed | Підтверджене |
| 2 | Processing | Обробляється |
| 3 | Shipped | Відправлене |
| 4 | Delivered | Доставлене |
| 5 | Cancelled | Скасоване |

git clone https://github.com/iEarsti/eRynok.git

cd eRynok

### 8.3. Налаштування підключення до бази даних

За замовчуванням проєкт використовує SQL Server LocalDB.

У файлі `appsettings.json` необхідно вказати рядок підключення:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=(localdb)\\MSSQLLocalDB;Database=eRynokDb;Trusted_Connection=True;TrustServerCertificate=True"
  }
}
```

Параметри підключення:

- `Server` — назва екземпляра SQL Server.
- `Database` — назва бази даних.
- `Trusted_Connection=True` — використання автентифікації Windows.
- `TrustServerCertificate=True` — довіра до сертифіката сервера.

Якщо використовується LocalDB, переконайтеся, що він встановлений і запущений.

Перевірити наявні екземпляри LocalDB:

```powershell
sqllocaldb info
```

Запустити стандартний екземпляр:

```powershell
sqllocaldb start MSSQLLocalDB
```

Якщо використовується звичайний SQL Server або SQL Server Express, рядок підключення потрібно змінити відповідно до назви встановленого екземпляра та способу автентифікації.

Наприклад, для SQL Server Express:

```json
"DefaultConnection": "Server=.\\SQLEXPRESS;Database=eRynokDb;Trusted_Connection=True;TrustServerCertificate=True"
```

### 8.4. Налаштування секретів через User Secrets

Проєкт використовує конфіденційні налаштування, які не повинні зберігатися в GitHub або відкритому `appsettings.json`.

Для локальної розробки використовується механізм **.NET User Secrets**.

Перейдіть у директорію backend-проєкту, де знаходиться файл `eRynok.csproj`:

```powershell
cd eRynok
```

Якщо User Secrets ще не ініціалізовані, виконайте:

```powershell
dotnet user-secrets init
```

Команду достатньо виконати один раз для проєкту.

#### Створення JWT-секрету

Для підпису JWT-токенів використовується конфігураційний параметр `Jwt:Key`.

Згенерувати криптографічно випадковий секрет довжиною 64 байти та зберегти його можна так (PowerShell):

```powershell
$bytes = New-Object byte[] 64
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
$jwtKey = [Convert]::ToBase64String($bytes)

dotnet user-secrets set "Jwt:Key" "$jwtKey"
```

Ця команда автоматично створює випадковий секрет і зберігає його в User Secrets.

Не потрібно вручну додавати `Jwt:Key` до `appsettings.json`.

#### Створення початкового адміністратора

Під час запуску застосунку система створює необхідні ролі та початковий обліковий запис адміністратора, якщо він ще не існує.

Для цього використовуються такі параметри:

- `Admin:Email` — електронна пошта адміністратора.
- `Admin:Password` — пароль адміністратора.
- `Admin:Name` — ім'я адміністратора.

Встановіть власні значення:

```powershell
dotnet user-secrets set "Admin:Email" "admin@erynok.local"
dotnet user-secrets set "Admin:Password" "YourStrongPassword123!"
dotnet user-secrets set "Admin:Name" "Administrator"
```

Замість наведеного прикладу пароля обов'язково використовуйте власний надійний пароль.

#### Перевірка збережених секретів

Переглянути список налаштованих параметрів можна командою:

```powershell
dotnet user-secrets list
```

У списку мають бути присутні:

```text
Jwt:Key
Admin:Email
Admin:Password
Admin:Name
```

Не публікуйте вивід цієї команди, оскільки він містить конфіденційні значення.

**Важливо:** User Secrets призначені для локальної розробки. Для розгортання застосунку на сервері необхідно використовувати безпечне сховище секретів або змінні середовища.

### 8.5. Створення та оновлення бази даних

Для управління структурою бази даних використовується **Entity Framework Core Migrations**.

Усі зміни структури моделей необхідно супроводжувати створенням відповідних міграцій.

#### Встановлення EF Core CLI

Якщо інструмент `dotnet-ef` ще не встановлений:

```powershell
dotnet tool install --global dotnet-ef --version 8.*
```

Якщо він уже встановлений, але потребує оновлення:

```powershell
dotnet tool update --global dotnet-ef --version 8.*
```

#### Створення міграції

Після зміни моделей або контексту бази даних створіть нову міграцію:

```powershell
dotnet ef migrations add MigrationName
```

Замість `MigrationName` вкажіть коротку назву змін, наприклад:

```powershell
dotnet ef migrations add AddOrderGroup
```

Міграції зберігаються в проєкті та повинні додаватися до Git-репозиторію.

#### Застосування міграцій

Для створення бази даних або оновлення її структури виконайте:

```powershell
dotnet ef database update
```

Команда застосує всі наявні міграції, які ще не були застосовані до бази даних.

#### Використання Package Manager Console у Visual Studio

Ті самі операції можна виконувати через **Tools → NuGet Package Manager → Package Manager Console**.

Команди:

```powershell
Add-Migration MigrationName
Update-Database
```

Якщо Visual Studio використовує декілька проєктів, переконайтеся, що і **Default Project**, і **Startup Project** вказують на backend-проєкт `eRynok`, у якому знаходяться `Program.cs`, `eRynokDbContext` та конфігурація застосунку.

#### Якщо міграції не створюються або виникають проблеми з базою даних

Під час розробки іноді виникають ситуації, коли локальна база даних не відповідає актуальним міграціям або EF Core не може коректно застосувати зміни.

Якщо локальна база даних більше не потрібна та її можна створити заново, допускається повне видалення бази з подальшим повторним застосуванням міграцій.

У Package Manager Console:

```powershell
Drop-Database
Update-Database
```

Або через термінал:

```powershell
dotnet ef database drop --force
dotnet ef database update
```

**Увага!** `Drop-Database` повністю видаляє базу даних разом з усіма даними. Використовуйте цю команду лише під час локальної розробки, коли дані можна втратити.

Якщо проблема полягає саме у відсутній міграції, спочатку створіть її за допомогою `Add-Migration` або `dotnet ef migrations add`, а вже потім виконуйте `Update-Database`.

Видалення бази даних не видаляє файли міграцій із проєкту. Не потрібно видаляти наявні міграції без розуміння наслідків.

### 8.6. Запуск застосунку

Перейдіть до директорії backend-проєкту, де знаходиться файл `eRynok.csproj`.

Виконайте:

```powershell
dotnet restore
dotnet build
dotnet run
```

Після запуску API буде доступне за адресою, зазначеною в консолі або у файлі `Properties/launchSettings.json`.

Для локального запуску frontend необхідно також переконатися, що адреса API у frontend-коді відповідає фактичній адресі запущеного backend.

Наприклад:

```javascript
const API_BASE_URL = 'https://localhost:7082/api';
```

Якщо використовується інший порт, його потрібно замінити.

### 8.7. Swagger

Для тестування API використовується Swagger UI.

Після запуску застосунку відкрийте адресу:

```text
https://localhost:<port>/swagger
```

або

```text
http://localhost:<port>/swagger
```

У Swagger можна переглядати доступні endpoints, надсилати запити та перевіряти відповіді API.

Для тестування захищених маршрутів необхідно отримати JWT-токен через `/api/Auth/login` та передати його в заголовку:

```text
Authorization: Bearer <JWT_TOKEN>
```

## 9. Структура бази даних та збереження даних

Для роботи з базою даних використовується контекст `eRynokDbContext`.

Взаємодія з SQL Server реалізована через Entity Framework Core.

ASP.NET Core Identity використовується для зберігання облікових записів користувачів і ролей.

Основні групи даних:

- Користувачі та ролі Identity.
- Профілі продавців і покупців.
- Категорії товарів.
- Товари.
- Групи замовлень.
- Замовлення.

Структура бази даних контролюється за допомогою EF Core Migrations. Після отримання змін проєкту з GitHub необхідно перевірити наявність нових міграцій та за потреби виконати:

```powershell
dotnet ef database update
```

## 10. Безпека

У проєкті реалізовано:

- Автентифікацію користувачів через JWT.
- Перевірку підпису та терміну дії токенів.
- Перевірку Issuer та Audience.
- Розмежування доступу за ролями.
- Перевірку прав користувача під час роботи з власними товарами та замовленнями.
- Зберігання паролів засобами ASP.NET Core Identity.
- Зберігання конфіденційних параметрів через .NET User Secrets під час локальної розробки.

JWT використовує такі конфігураційні параметри:

| Параметр | Значення |
|---|---|
| `Jwt:Key` | Секретний ключ підпису токенів |
| `Jwt:Issuer` | `eRynok.Api` |
| `Jwt:Audience` | `eRynok.Client` |
| `Jwt:ExpiresInMinutes` | `60` |

Секретний ключ `Jwt:Key` та облікові дані початкового адміністратора не повинні зберігатися у відкритому вигляді в репозиторії.

## 11. Поточний стан проєкту

Реалізовано основні функції онлайн-маркетплейсу:

- Розділення логіки на контролери, сервіси, репозиторії, моделі та DTO.
- Автентифікація та авторизація за допомогою JWT.
- Управління ролями Seller, Buyer та Admin.
- Початкове створення ролей і адміністратора.
- Окремі профілі продавців і покупців.
- CRUD-операції для товарів, категорій і користувачів.
- Перевірка прав доступу відповідно до ролей.
- Створення та управління кошиком покупця.
- Обмеження одним `OrderGroup` для кожного покупця.
- Створення замовлень і збереження ціни товару на момент замовлення.
- Зміна кількості товарів у кошику.
- Перегляд і фільтрація замовлень.
- Зміна статусів замовлень продавцями та адміністраторами.
- Валідація вхідних даних.
- Перевірка існування пов'язаних записів.
- Асинхронна взаємодія з базою даних.
- Обробка помилок із відповідними HTTP-статусами.
- Керування структурою бази даних через Entity Framework Core Migrations.

База даних створюється та оновлюється за допомогою Entity Framework Core Migrations.

Авторизація та розмежування доступу реалізовані на рівні API, а доступ до окремих операцій додатково перевіряється бізнес-логікою сервісів.
